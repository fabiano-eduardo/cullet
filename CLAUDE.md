# cullet — context for AI agents

## What this project is

`cullet` is an opinionated catalog of architectural building blocks for TypeScript projects. It ships a CLI and a set of kits.

Being an importable TypeScript module is **not** an invariant of a kit — it is an opt-in capability. A kit declares its nature via `kind` in `meta.json`:

- **`foundation` / `capability`** — importable library kits (the default when `kind` is absent). Consumed two ways:
  - **Direct import**: `import { Entity } from 'cullet/erp-core'`
  - **Full-control copy**: `npx cullet fc erp-core@1.0.0` (copies kit `src/` into the consumer project and registers a tsconfig alias)
- **`tooling`** — copy-first kits (e.g. an AI-agent harness). They declare `delivery.copy.placement` and ship a `files/` payload that `npx cullet fc <kit>` merges into that placement (e.g. `.claude/`). Optionally a tooling kit may **also** opt into an importable surface by declaring `entryPoint` + `delivery.import` (e.g. a typed `defineAgentConfig` helper): then it is consumable straight from node_modules (`import { ... } from 'cullet/<kit>'`) with no copy, and `cullet info <kit> --alias` registers the tsconfig alias.

The kind-conditional contract (library kits require `entryPoint`/`philosophy`/`compatibility`/`src/`; tooling kits require `delivery.copy` + a payload dir, and a tooling kit that declares `delivery.import` must also declare an existing `entryPoint`) is enforced imperatively in `scripts/validate-kit.mjs`, since the hand-rolled schema validator has no `if/then`.

## Key directories

The repo is an npm workspace (`packages/*`). Kit source and the CLI are packages; the top-level `kits/` folder holds authoring guides only, not kit source.

| Path                            | Purpose                                                                                                                  |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `packages/`                     | Workspace packages: the CLI (`cullet`, in `packages/cli/`) and the kits, one package per kit (e.g. `packages/erp-core/`) |
| `packages/cli/`                 | CLI entry point (`cullet list`, `cullet doctor`, `cullet fc`, `cullet info`)                                             |
| `packages/cli/registry/index.json` | JSON catalog of kits consumed by the CLI                                                                             |
| `kits/`                         | Kit authoring docs only (`AUTHORING.md`, `VERSIONING.md`) — not kit source        |
| `docs/`                         | Starlight docs site deployed to GitHub Pages                                                                             |
| `dist/`                         | Built output (gitignored, regenerated by `npm run build`)                                                                |
| `scripts/`                      | Build helpers (`sync-kit-deps.mjs`, `validate-kit.mjs`, `new-kit.mjs`, …) and the kit spec schema (`kit-spec.schema.json`) consumed by `validate-kit.mjs` |
| `templates/`                    | Scaffolding templates used by `new-kit`                                                                                  |
| `tests/`                        | Unit and E2E test suites                                                                                                 |

The kit resolver in `packages/cli/src/registry/catalog.ts` reads each kit from its package dir (`packages/<name>/`) and probes a legacy `kits/<name>/versions/<v>/` path as a backward-compat fallback. That fallback is intentional compatibility, not an in-progress layout migration — `packages/*` is the canonical layout.

## Development commands

```bash
npm run build          # tsdown build for the workspace packages
npm run typecheck      # tsc --noEmit (both tsconfig.json and tsconfig.test.json)
npm run test           # vitest unit tests
npm run test:e2e       # vitest E2E smoke tests
npm run validate-kits  # validates registry integrity
npm run sync-kit-deps  # syncs workspace kit peerDependencies from meta.json
npm run docs:build     # builds the Starlight docs site (after npm --prefix docs install)
npm run release:dry-run  # build + pack + check contents (no publish)
```

## Release process

Releases are fully automated via GitHub Actions (`.github/workflows/release.yml`).

**How to release:**

1. Add a changeset in the PR (`npm run changeset`).
2. Merge to `main`; the action opens or updates the release PR with version and changelog changes.
3. Merge the release PR; the action runs typecheck → validate-kits → sync-kit-deps:check → tests → e2e → pack-validate → publish → GitHub Release.

**npm authentication: NPM_TOKEN + provenance attestation**

Publishing requires an npm Automation token stored as the `NPM_TOKEN` GitHub Actions secret. The workflow also uses `id-token: write` so npm provenance is attached during publish.

`--provenance` uses the `id-token: write` OIDC permission to attach a signed provenance attestation to the package — this is separate from authentication and does not replace the token.

The publish command executed by the action is:

```bash
npm run release
# internally runs: npm run release:dry-run && changeset publish
```

Note: npm does **not** support token-free OIDC publishing (unlike PyPI). `--provenance` and OIDC are for attestation only.

## Adding a new kit

```bash
npm run new-kit -- <kit-name>                 # foundation (library) kit, the default
npm run new-kit -- <kit-name> --kind tooling  # copy-only kit (ships a files/ payload)
```

The script scaffolds the kit under `packages/<name>/` from `templates/kit/` (foundation) or `templates/tooling-kit/` (tooling) and updates `packages/cli/registry/index.json`.

## Constraints and conventions

- ESM-only (`"type": "module"` in `package.json`).
- Node ≥ 18.
- `pino` is an optional peer dependency; `zod` is a required peer dependency.
- `dist/`, `node_modules/`, `*.tgz`, `tmp/` are gitignored and should never be committed.
- Never commit secrets, tokens, or credentials. Release automation depends on `NPM_TOKEN`; provenance attestation depends on OIDC.
